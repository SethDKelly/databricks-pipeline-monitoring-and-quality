# 009 — Initial Roadmap

## Status authority

This roadmap defines **phase ownership and sequence**, not live repository phase status.

Current phase progression is declared only in [`../README.md#current-state`](../README.md#current-state). Any historical status wording in earlier roadmap revisions is status-at-time-of-writing rather than current authority.

The detailed roadmap text that previously occupied this file is preserved byte-for-byte as [`history/009_initial_roadmap_pre_phase_006_exit.md`](history/009_initial_roadmap_pre_phase_006_exit.md). Its phase-status statements are historical snapshots and are superseded by the canonical documentation index.

## Durable roadmap sequence

### Phase 001 — Product Foundation and Concept Discovery
Establish product purpose, actors, terminology, architectural principles, security/governance foundations, ecosystem lifecycles, MVP boundary, and Concept Design method.

### Phase 002 — Concept Specifications
Define independently understandable product concepts and their operational principles, state, actions, invariants, ambiguity behavior, and boundaries.

### Phase 003 — Concept Synchronizations and Ecosystem Scenarios
Define how accepted concepts coordinate across end-to-end ecosystem scenarios without collapsing into architecture.

### Phase 004 — Evidence, Time, and Causality Refinement
Refine evidence sufficiency, temporal semantics, causal epistemics, exposure, readiness, control evidence, and historical replay.

### Phase 005 — Governance, Authority, Semantics, Policy, and Capability Refinement
Refine Assertion Authority, normative governance, Capability Authorization, high-consequence authority, disclosure, and related historical semantics.

### Phase 006 — Health, Freshness, Quality, Metrics, and Result-Timing Refinement
Define metric/check vocabulary and profiles; structural/schema compatibility; Baseline and statistical comparability; thresholds, warnings, waivers, and Assessment; transformation reconciliation; composite health; evidence freshness/maturity/suitability; and functional result timing.

### Phase 007 — Lineage, Change, Investigation, Impact, Safeguard, and Execution-Control Refinement
Refine historical Lineage/topology, Change Intent realization, Deployment and realized Change, prospective blast radius, execution reconstruction, Investigation lifecycle, downstream encounter/exposure/consequence, Propagation Safeguard behavior, Execution Gate behavior, and historical operational replay.

### Phase 008 — Business Questioning and Explanation
Define question types, evidence-grounded Explanation structures, audience-specific authorized projections, uncertainty/status communication, progressive result maturity, and historical/retrospective explanation behavior.

### Phase 009 — Integration Contracts, Source Authority, and Evidence Availability
Map accepted functional requirements to actual Databricks, Unity Catalog, Git, GitHub Actions, DQX, Metric Views, Collibra, Immuta, downstream-consumption, authorization, authority-rule, and control-evidence capabilities. Characterize source availability, latency, retention, cost, and observability without mistaking availability for authority.

### Phase 010 — Technical Architecture
Select implementation architecture only after functional semantics and integration evidence are sufficiently stable. Evaluate persistence, graph/history representation, ingestion/synchronization, authority/authorization realization, monitoring deployment, validation placement, safeguard/gate realization, metric computation/storage, Explanation delivery, testing/observability, and fast-path versus asynchronous analysis.

### Later MVP validation
Translate accepted architecture and timing objectives into implementation phases and measurable MVP acceptance criteria only after the earlier design and integration work justify them.

## Roadmap discipline

- Phase descriptions may state durable ownership and sequencing.
- Current/next/complete status belongs in `docs/README.md#current-state`.
- Phase-specific READMEs may state their own internal group status.
- Historical snapshots may retain old status wording when clearly labeled historical.
- Living indexes and contributor/agent guidance should reference canonical status instead of maintaining independent copies.
- Implementation selection remains deferred until the roadmap phase that explicitly owns it.
