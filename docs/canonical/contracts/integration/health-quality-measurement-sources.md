# Health, Schema, Metrics, Expectations, Baselines & Reconciliation Evidence

**Canonical key:** `integration.group-04`

**Kind:** INTEGRATION CONTRACT

**Authority:** CANONICAL CURRENT AUTHORITY

**Migration record:** `stable_family.INTG`

**Stable IDs:** INTG-084–INTG-119

**Owns current question:** What can evaluated structural, DQ, metric, profiling and monitoring sources actually evidence under the accepted Observation/Baseline/Expectation/Assessment health model?

## Canonical source findings

Preserve the chain:

**exact subject/run/output/context → realized structural or metric/check source evidence → Observation → explicit Baseline/reference and/or governed Expectation → Assessment → transformation/reconciliation/composite-profile composition → freshness/result-suitability context**.

Realized schema ≠ governed semantic definition ≠ consumer contract ≠ compatibility Assessment. Declared constraints ≠ empirical integrity. DQX rule/profile availability ≠ governed Expectation; DQX criticality/action ≠ business severity or control truth. Lakeflow expectation action ≠ normative result. Metric View platform specification version ≠ organization-governed metric-definition revision. Profile metric ≠ Baseline membership ≠ drift Assessment ≠ health violation. Vendor anomaly/root-cause/downstream-impact fields are source assertions/context and cannot bypass DMTZ Causal Claim or Impact semantics.

Commit freshness ≠ event freshness. Generic exact multi-input current-cycle alignment remains conditional where input-version evidence is absent. Historical Assessment requires retained definitions as well as values. Strong health negatives require expected opportunity, adequate source/population/history coverage and source health.

## Stable contracts

### INTG-084 — Current Realized Schema Metadata Surface
Use visible current metadata as realized structural evidence for the exact object/principal view; it is not by itself a consumer compatibility or governed-semantic conclusion.

### INTG-085 — Table-History Structural Change & Replay
Use retained table/version history for bounded structural-change replay only within its actual history/time-travel retention and provenance envelope.

### INTG-086 — Schema Identity, Rename & Recreate Continuity
Preserve object identity across rename/recreate only where identifiers/history establish continuity; name reuse is not identity continuity.

### INTG-087 — Constraint Declaration & Enforcement Separation
Declared PK/FK/constraint metadata describes declarations/engine semantics; empirical uniqueness/referential-integrity health requires actual measurement or another sufficient source.

### INTG-088 — Consumer-Specific Compatibility Source Gap
No generic realized-schema source proves every consumer/interface compatibility contract; consumer-specific requirements remain explicit inputs/gaps.

### INTG-089 — DQX Surface, Version & Pinning
Treat DQX capability/results relative to the exact DQX release/configuration used; historical interpretation requires sufficient version/config provenance.

### INTG-090 — DQX Rule Identity, Definition & Storage
Preserve exact rule identity/definition/storage revision separately from any later governed Expectation adoption.

### INTG-091 — DQX Detailed Result Observation
Treat detailed DQX issue/result records as Observations at their actual row/dataset/run/input grain, not direct normative Assessments.

### INTG-092 — DQX Summary Metrics & Run Binding
Summary metrics become usable only with reliable rule-set/run/input/result binding; counts/ratios without that context cannot be generalized.

### INTG-093 — DQX Profiling / Rule-Generation Candidate Boundary
Profiler/AI-generated checks are candidates, not governed Expectations or authoritative health criteria until explicitly adopted.

### INTG-094 — DQX Criticality / Action Governance Boundary
DQX `warn`/`error` or action configuration is source behavior, not automatically business severity, waiver, Assertion Authority, Gate or control policy.

### INTG-095 — Lakeflow Expectation Definition & Action
A Lakeflow expectation may implement a governed criterion only when exact definition/revision/authority/applicability are established; `warn/drop/fail` action remains separate from normative result.

### INTG-096 — Lakeflow Expectation Event-Log Metrics
Use event-log pass/fail/drop metrics only for qualifying flows/updates and exact expectation identity under documented emission semantics.

### INTG-097 — Lakeflow Fail-Expectation Metric Gap
A fail-update violation can be known while the usual invalid/population metrics are unavailable; missing counts remain an evidence gap rather than fabricated zero.

### INTG-098 — Metric-View Definition & Measure Semantics
Metric Views can centralize reusable measure semantics, but source/joins/filters/dimensions/measures must be bound to the exact governed metric definition.

### INTG-099 — Metric-View Specification Version vs Definition Revision
Keep Databricks Metric View YAML/spec/runtime version separate from organization-governed metric-definition revision.

### INTG-100 — Metric-View Query Observation & Grain
Treat a metric result as an Observation only with exact definition, grouping/filter/parameter/window and source-context grain.

### INTG-101 — Metric-View Materialization & Freshness Boundary
Materialization/cache refresh is an optimization/availability fact, not automatically a DMTZ freshness/currentness criterion.

### INTG-102 — Data-Profiling Profile Metrics as Observations
Profile metrics are descriptive Observations at configured windows/slices; they do not automatically establish Baseline membership or normative health.

### INTG-103 — Data-Profiling Drift & Baseline Semantics
Configured drift/baseline comparison is source evidence; framework Baseline membership, regime, comparability and Assessment remain governed by HLTH semantics.

### INTG-104 — Data-Profiling Custom Metric Definition
Custom metric results require exact metric-definition/version/authority and window/slice binding before use in Baseline or Assessment reasoning.

### INTG-105 — Anomaly-Detection Freshness / Completeness Model
Vendor learned-pattern freshness/completeness results are source-owned Assessments for their documented model/dimension, not substitutes for explicit SLAs or all health dimensions.

### INTG-106 — Anomaly-Detection Health-Status Projection
Vendor table-health projection is a bounded source projection and cannot become a universal DMTZ composite-health state.

### INTG-107 — Anomaly-Detection Root-Cause / Impact Label Boundary
Vendor root-cause/downstream-impact labels are contextual assertions/candidates only and cannot bypass Investigation, Causal Claim or Impact evidence/authority gates.

### INTG-108 — Baseline Membership, Version & Authority Contract
Source-native historical/reference tables are candidates for Baseline construction; membership/regime/version/authority remain explicit framework contracts.

### INTG-109 — Measurement Window, Slice & Cohort Binding
Every measurement binds its exact time window, slice/cohort/population, grain and parameters; aggregate similarity cannot silently answer a narrower proposition.

### INTG-110 — Measurement ↔ Run / Output-Version Binding
Bind health measurements to an exact run/output version only where source identifiers/provenance establish the association; latest/current state is not a substitute.

### INTG-111 — Reconciliation Source Evidence Contract
Reconciliation requires exact transformation/version, inputs/output, populations, grain, keys/measures, window and current-cycle semantics.

### INTG-112 — Join / Fan-Out Metric-Semantics Boundary
Join/cardinality declarations or apparent metric agreement do not substitute for empirical fan-out/key/reconciliation evidence where incorrect joins can alter measures.

### INTG-113 — Commit Freshness vs Event Freshness
Commit freshness and event-time/ingestion-latency freshness are different propositions; a source supporting one does not automatically support the other.

### INTG-114 — Current-Cycle Alignment & Input-Version Gap
Exact current-cycle health is conditional when generic run-specific multi-input version consumption is unresolved; current/latest source state cannot fill that gap.

### INTG-115 — Result Timing, Scan / Refresh & Availability
Keep rule execution, flow/update event, query/materialization refresh, profiling refresh, anomaly scan, table commit, result availability and retrieval clocks distinct.

### INTG-116 — Health-Source Historical Replay & Retention
Historical health replay requires retained results plus the exact rule/metric/Baseline/profile definition/revision needed to interpret them.

### INTG-117 — Missing Metric / Check / Schema Negative Claims
`No schema change/failed check/anomaly/metric/quality issue` requires expected opportunity plus sufficient source/population/history coverage and source health; disabled/failed/filtered/expired sources are limitations.

### INTG-118 — Health-Source Conflict & Composition
Conflicting health sources remain proposition/definition/grain specific; no source count, vendor status or recency creates a hidden winner or global health score.

### INTG-119 — Group 04 Health Source Matrix & Group 05 Handoff
Pass Observations/Assessments forward only with exact subject/version/window/population/provenance/coverage limits; failed checks or anomalies do not establish publication, encounter, exposure, effect, consequence or cause.

## Architecture boundary

This contract selects no DQX deployment mode, rule-store schema, metric warehouse, monitoring schedule, Baseline algorithm, anomaly model, reconciliation engine, retention service, alerting architecture or health-serving API.
