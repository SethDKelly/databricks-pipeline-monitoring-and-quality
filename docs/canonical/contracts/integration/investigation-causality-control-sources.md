# Investigation, Causality, Safeguard, Gate & Control Evidence

**Canonical key:** `integration.group-06`

**Kind:** INTEGRATION CONTRACT

**Authority:** CANONICAL CURRENT AUTHORITY

**Migration record:** `stable_family.INTG`

**Stable IDs:** INTG-154–INTG-200

**Owns current question:** What can evaluated investigation/runtime/audit/control sources establish about inquiry, causal support, Safeguard/Gate lifecycle, enforcement, prevention and historical control state?

## Canonical source findings

Three source chains remain independent:

1. **Investigation → lead/localization → discriminating evidence → explicit Causal Claim → REF/AUTH-governed causal status**.
2. **protected state/path/cohort → Safeguard proposal/authorization/request → control acceptance → enforcement → encounter result → REF-028 prevention where justified → release/reopening → independent recovery**.
3. **Gate opportunity + criterion/profile → evidence suitability/readiness → HOLD/ADMIT/override/fallback decision → delivery/acceptance → enforcement → execution/non-execution → independent operational/Impact effects**.

Localization/lead ≠ causality; causal `confirmed` remains REF-017 + AUTH-034 gated. Audit request ≠ response ≠ changed target state ≠ effective enforcement. Policy configured ≠ applicable ≠ applied ≠ allowed/denied/transformed outcome. Safeguard enforcement ≠ prevention; no opportunity earns no prevention credit; one denied path does not prove global protection. Databricks cancellation is post-start interruption, not pre-start HOLD. GitHub environment protection applies only to the job/deployment opportunity it actually protects; mapping it to a Databricks run requires explicit correlation. HOLD/ADMIT ≠ execution outcome. Missing control telemetry ≠ fail-open/fail-closed.

## Stable contracts

### INTG-154 — Cross-Source Investigation Evidence Assembly
Compose Investigation evidence from source-owned propositions with explicit provenance, scope, time, coverage and limitations; assembly does not create causal truth.

### INTG-155 — Investigation Trigger & Bounded Inquiry Source
Treat incident/alert/anomaly/control/human records as triggers for a bounded inquiry, not proof that a cause already exists or has been identified.

### INTG-156 — First-Observed Localization Evidence
First observed deviation is an evidence-localization proposition bound to observable source coverage and time; it is not root cause.

### INTG-157 — Earliest-Evidenced Change Localization
Earliest evidenced state change remains bounded by source history/coverage and is not automatically the earliest real change or cause.

### INTG-158 — Transformation / Reconciliation Boundary Localization
A first transformation/reconciliation mismatch can localize inquiry but remains distinct from causal attribution.

### INTG-159 — Consumer-Effect Localization
First observed consumer effect is an Impact-localization fact and cannot be promoted into root cause merely by being downstream or early.

### INTG-160 — Lead Generation Provenance
Every lead retains who/what generated it, searched scope, supporting context and limitations; ranking, seniority, graph distance or tool origin does not create causal status.

### INTG-161 — Lead Exclusion Negative-Evidence Contract
Excluding a lead is a strong negative that requires proposition-specific opportunity/coverage evidence; lack of support or missing telemetry is not rejection.

### INTG-162 — Human Review & Annotation Record
Human review/annotation is retained as authored evidence/context with its actual Assertion Authority; analyst agreement alone does not confirm cause.

### INTG-163 — Automation / Model Research Record
Automated/model/RCA outputs are research/derived evidence unless separately authoritative; model confidence/ranking does not bypass causal or evidence gates.

### INTG-164 — Causal Proposition Identity & Source Binding
Bind every causal proposition to exact cause, effect, role, population/scope, effective interval, mechanism assumptions and knowledge cut before evaluating sources.

### INTG-165 — Causal Support & Contradiction Evidence Roles
Runtime/version contrasts, reconciliation, populations, timing, interventions and control evidence retain claim-relative support/contradiction/limitation roles rather than universal ranking.

### INTG-166 — Causal Confirmation Authority Requirement
No Databricks/GitHub/Immuta/vendor/human source automatically owns `confirmed`; confirmation remains jointly constrained by REF-017 evidence and AUTH-034 authority.

### INTG-167 — Intervention / Remediation Contrast Evidence
Rollback/rerun/remediation/intervention contrasts can discriminate causal claims only with exact intervention/state/population/timing and alternative-cause context.

### INTG-168 — Temporal / Mechanism Discrimination & Counterevidence
Temporal order/mechanism consistency/counterevidence can support or weaken a bounded claim but does not convert correlation into confirmation.

### INTG-169 — Investigation / Causal Historical Replay
Historical Investigation/Causal replay composes source-specific history and availability-by-K; later evidence cannot be backfilled into earlier knowledge cuts.

### INTG-170 — Databricks Audit Control-Fact Surface
Use qualifying audit events as bounded control/action facts with actor/action/request/response/time context and documented retention/coverage; audit presence alone is not enforcement proof.

### INTG-171 — Audit Request vs Response / Outcome Boundary
Preserve **request recorded → response returned → target state changed → effective enforcement during relevant opportunity** unless documented semantics justify collapsing a specific step.

### INTG-172 — Unity Catalog Grant / Revoke as Control Action
Grant/revoke evidence is strong for the exact Unity Catalog privilege plane it controls; it does not prove every alternate path or historical enforcement state.

### INTG-173 — Current Privilege State vs Historical Enforcement
Current privilege/access state cannot be projected backward as historical enforcement without qualifying historical action/state evidence.

### INTG-174 — Immuta Policy Definition / Change Surface
Policy definition/change history establishes configured policy state for covered sources/populations; configuration is not query-time enforcement.

### INTG-175 — Immuta Query-Time Applied-Policy Evidence
A qualifying applied-policy query record can strongly evidence that policy application for the bounded user/data/query path; it does not establish global coverage.

### INTG-176 — Immuta Denial / Entitlement Enforcement Evidence
Denial/entitlement records can evidence a bounded enforcement outcome, but remain subject to registration, integration, user-population, query-path and audit coverage.

### INTG-177 — Immuta Coverage, Registration & Audit Limits
Immuta enforcement/audit claims are limited by registered users/data sources, integration version/scope, retention and audit configuration; uncovered paths remain unresolved.

### INTG-178 — Safeguard Proposal / Authorization / Request Record
Safeguard proposal, authorization and request are distinct lifecycle facts and do not establish control acceptance or effective enforcement.

### INTG-179 — Safeguard Acceptance & Effective Enforcement Evidence
Establish acceptance/effective enforcement from evidence that the protected surface/path actually applied the control; configured/active status alone is insufficient when opportunity-specific proof matters.

### INTG-180 — Safeguard Protected-State / Path / Cohort Binding
Bind each Safeguard to exact suspect/protected state, path, cohort/population and effective interval before evaluating coverage or prevention.

### INTG-181 — Safeguard Partial & Alternate-Path Coverage
Partial enforcement or one controlled path cannot establish global protection where material alternate paths/populations remain unresolved.

### INTG-182 — Safeguard No-Opportunity / Prevention Boundary
No encounter opportunity means there was nothing to prevent; absence of exposure without a relevant opportunity earns no Safeguard prevention credit.

### INTG-183 — REF-028 Prevented-Exposure Composition
Prevented exposure requires relevant encounter opportunity, path through the protected surface, effective enforcement, negative suspect-state encounter and sufficient alternate-path coverage.

### INTG-184 — Safeguard Release / Regrant / Effective Reopening
Release/regrant/reopening requires evidence of the control transition and restored path availability; release is not recovery/currentness proof.

### INTG-185 — Safe-State / Non-Delivery Effect Boundary
Safe stale serving/non-delivery or other safe-state effects remain health/Impact outcomes distinct from Safeguard prevention and recovery.

### INTG-186 — Overlapping Safeguards & No Hidden Attribution
Multiple Safeguards can overlap; observed non-exposure does not automatically attribute prevention to one control without discriminating evidence.

### INTG-187 — Databricks Jobs Cancel as Post-Start Interruption
Databricks cancellation acts on an existing run/task and is post-start interruption evidence, not a pre-start Execution Gate HOLD.

### INTG-188 — Native Output-Hold / Quarantine Gap
No universal native quarantine/hold is assumed across all Databricks table/version/dashboard/export/API/application paths; realization remains path-specific or unsupported.

### INTG-189 — GitHub Environment Protection as Gate Surface
GitHub protected environments can provide strong pre-runner Gate semantics for the exact Actions job/environment opportunity they protect.

### INTG-190 — GitHub Reviewer Approval, Reject, Bypass & Wait Semantics
Required-review approval, rejection, bypass and wait timer are distinct GitHub control outcomes; bypass requires explicit DMTZ override authority/scope mapping.

### INTG-191 — GitHub Custom Deployment Protection Rule
Custom protection-rule decisions are Gate decisions for that configured GitHub rule; they do not inherit truth authority over external observability/quality sources consulted.

### INTG-192 — Databricks `Run if` / `If/else` Gate Mapping
Databricks conditional execution can realize a Gate only with explicit mapping of Gate/profile/opportunity, criterion revision, operands/source evidence, condition evaluation and blocked/selected branch result.

### INTG-193 — Gate Criterion / Readiness Source Binding
Criterion/profile identity, Assertion Authority, Capability Authorization and evidence suitability remain explicit; task names or booleans do not automatically become DMTZ readiness.

### INTG-194 — Gate Decision, Delivery & Acceptance Evidence
Preserve **decision issued → delivered → accepted/acknowledged → effective barrier/permissive state** when sources expose separate stages; missing stages remain unknown.

### INTG-195 — HOLD Enforcement & Contradictory Start
Reliable execution start during an applicable unsuperseded HOLD contradicts full HOLD enforcement; conversely, no run does not prove HOLD without opportunity/control/execution coverage.

### INTG-196 — ADMIT Barrier Removal & Non-Execution
ADMIT can establish barrier removal/permissiveness when evidenced; it does not prove that execution actually occurred.

### INTG-197 — Override, Fallback, Timeout & Escalation Evidence
Override preserves readiness truth; fallback configuration/trigger/selection/enforcement are distinct, and timeout/escalation is not automatically an admission decision.

### INTG-198 — Multiple Gates & Safeguard Composition
Multiple Gates/Safeguards have no hidden universal precedence; composition, scope, exceptional paths and effective enforcement must be explicit.

### INTG-199 — Control Telemetry Failure & Historical Replay
Missing/conflicting/degraded control telemetry or expired history never proves fail-open, fail-closed, successful HOLD/Safeguard, fallback application or control-effect causality.

### INTG-200 — Group 06 Source Matrix & Group 07 Handoff
Pass Investigation/localization, exact Causal Claim status/basis and control lifecycle facts forward only with proposition identity, authority, T/K, coverage, retention and authorization limits; unresolved stages stay unresolved.

## Architecture boundary

This contract selects no incident/case system, RCA algorithm, causal-inference engine, approval workflow, quarantine/ACL/routing implementation, GitHub App, Databricks task design, Gate service, event store, retry/fallback mechanism, control-state store or UI.
