# Program Completion Definition

DMTZ does not have one universal `done` state; completion is profile-based.

## Profile 1 — MVP implementation complete

Implementations **001–008** complete with:

- the original MVP proof scenarios executable against representative pilot evidence;
- deterministic evidence-to-Explanation flow;
- Databricks/GitHub acquisition and canonical history;
- identity/scope/authority/authorization;
- health/quality/change/Lineage/Impact evidence;
- Investigation/Causal Claim/historical replay;
- governed API/UI;
- pilot operational/security/SLO/cost readiness;
- release-candidate exit review.

This is the first defensible product MVP.

## Profile 2 — Enterprise passive-monitoring platform complete

Implementations **001–009 and 011** complete, with 010 skipped if active control is not a product commitment.

Adds:

- scale/multi-tenant hardening;
- optional governance/security integrations actually required by customers;
- enterprise retention/residency/administration;
- performance/capacity validation at target scale;
- production operational ownership and support readiness.

## Profile 3 — Full active-control enterprise platform complete

Implementations **001–011** complete, including active Execution Gate / Propagation Safeguard scope.

Adds:

- deterministic control decisions;
- governed enforcement adapters;
- bypass/alternate-path coverage;
- prevention evidence and release/recovery semantics;
- SC-06 isolation/SLOs;
- control-plane production acceptance.

## Completion does not mean

- every source/vendor is supported;
- every pipeline has perfect Lineage;
- all causality is automatically confirmable;
- all downstream business consequence telemetry exists;
- every optional integration is installed;
- all unknowns disappear.

Enterprise-grade completion means the product correctly represents its supported/partial/unknown/unsupported boundaries and operates reliably within its declared capability profile.

## Post-completion evolution

After 011, new sources/features should enter through the same contracts:

capability discovery → bounded proposition support → adapter evidence/coverage → canonical mapping → deterministic evaluation → authorization-aware serving → executable scenarios → operational acceptance.

Do not create a new semantic shortcut for each new vendor.
