## Primary questions

- How is Git revision/change intent bound to deployment attempt, activation and exact run without timestamp/name convenience?
- What immutable attestation is required for bundle/workspace-source runs whose commit cannot be learned natively?
- How is composite run-specific implementation state represented across code/config/parameters/runtime/libraries/environment?
- How are exact input/output versions and multi-input consumption represented where instrumentation exists?
- How do health measurements bind exact entity/run/output/version/profile/definition revisions?
- How are event-time freshness and current-cycle alignment represented?
- How are Lineage edges persisted with relationship type, effective time, source evidence and coverage limitations?
- How are consumer encounter, cache/copy/result state and exact affected-version exposure distinguished?
- How are downstream technical/analytical/business effects represented without manufacturing consequence or causality?
- How does Group 04 acquisition coverage constrain `no run`, `no output`, `not exposed`, `no effect` and other negatives?

## Boundary

Lineage traversal must not manufacture consumption, exposure, effect, consequence, or causality. Current/latest state cannot substitute for run-/version-specific evidence when the proposition requires exact binding.

Group 05 must treat acquisition coverage and integration health as evidence-condition inputs, never as monitored-domain state.

## Handoff

After Group 05 acceptance, Group 06 may build Investigation/reasoning/replay/Explanation over exact operational, health, lineage and Impact evidence without inventing missing runtime bindings.
